# CloudServe architecture decision review

Reviewed on 16 November 2026 against the capstone's unattended-run gate, 29 approved articles, 500 development tickets, 80 visible validation tickets and current prototype tests. This updates the provisional ADRs in `Research/07_architecture_decisions.md`; it does not assert that unrun alternatives are inferior on measured quality.

| Decision | Alternatives considered | Current choice and evidence | Revisit when |
|---|---|---|---|
| Deployment shape | One modular app; separate ingestion/retrieval/API microservices | One FastAPI app with two logical pipelines and React. A source-only copy passed tests/build/batch. Microservices would add startup and consistency risk before independent scaling is measured. | Serving and ingestion load conflict, or a production reliability requirement needs independent scaling. |
| Knowledge authority | Vector index as sole KB; governed documents with indexes; live source lookup | Governed source/version store plus lexical index and optional dense index. Historical citations resolve after publication. | Permissions and multi-source updates need a stronger database or index transaction coordinator. |
| Agent roles | One general agent; two broad agents; six roles on every ticket; six conditional bounded roles | Six distinct responsibilities across knowledge and ticket pipelines. Source Intake and Triage are conditional; deterministic policy and release gate own final actions. Current role classes and 42 tests support local behavior, not incremental-quality superiority. | Human-labelled agent-level evaluation shows a role adds cost without benefit. |
| Routing | LLM decides tool/action; deterministic business rules; every ticket through RAG | Deterministic protected-intent and evidence rules. Same input/version repeats its decision in isolated stores; no model may override a protected rule. | Calibrated risk–coverage evidence supports threshold changes. |
| Retrieval | Lexical only; dense only; hybrid; graph retrieval | Lexical is the safe release baseline. Dense and hybrid candidate ranking exist; a real Azure index build was blocked by DNS, so no retrieval winner is claimed. | Passage gold, Recall@k, MRR, no-answer and latency comparisons are available. |
| Models and embeddings | OpenRouter; Azure GPT-4o/o3-mini/ada-002; local extractive + MiniLM | Extractive mode is default. Chroma `all-MiniLM-L6-v2` is the active 384-dimensional dense index; ada-002 is legacy optional. GPT-4o is an optional steward/query/answer tool and o3-mini is selected only for Azure triage/verification. | Human-adjudicated quality, latency and configured cost justify a different routing policy. |
| Graph and ontology | Bounded document GraphRAG now; auto-ontology later | Execute one-hop traversal over curated `related_docs`, but intersect every expansion with the intent policy's authorised documents. Display graph/traversal evidence in the UI. Do not claim entity ontology or measured graph gain until passage gold exists. | Human passage gold plus a labelled multi-hop task justifies entity extraction or auto-ontology. |

The six roles are Source Intake, Knowledge Steward, Triage, Evidence, Answer and Verification. Their boundaries and tools are in [architecture.md](architecture.md) and `Research/10_six_agent_design.md`. The current implementation does not run six Azure calls per ticket. The [PRD v1](PRD_v1.md) records the same decision and its revision trigger. Open risks are identity/tenant authorization, human claim gold, live dense retrieval, browser/deployment rehearsal and production monitoring.
